## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
TASK-0192.05 delivers a Protector that seals, opens and builds search terms by qualified column name. That is the AWS Database Encryption SDK level of ease: correct, but the embedder still calls the library around every protected column on every query and still types the schema.table.column string by hand. The stated goal — import the crate, declare the policy, and the fields are encrypted and decrypted — needs one more layer, at the CipherStash Protect level.

Ship a dbsec-derive proc-macro crate:

    #[derive(Protect)]
    #[dbsec(table = "public.users", row_key = "id")]
    struct User {
        id: Uuid,
        #[dbsec] ssn: String,
        #[dbsec(searchable)] email: String,
        notes: String,
    }

Generated: User::seal(&self, &Protector) -> Result<UserSealed>, UserSealed::open(&Protector) -> Result<User>, and a per-searchable-field term builder (User::email_term(&Protector, &str)) for equality predicates. UserSealed holds Vec<u8>/String in the stored wire form so it can be bound and decoded by sqlx directly.

Why a record-level derive and not per-value sqlx Encode/Decode newtypes: Decode has no access to a Protector and no access to the row, so row-bound (DBS3) columns — the property dbsec is ahead on — cannot be transparent at the value level. A struct-level macro sees the row_key field, derives every qualified column name from the attributes, and never lets the caller hand-type the AAD convention. Per-value newtypes may come later for non-row-bound columns only.

Also required, because the macro needs them: typed RowKey constructors in dbsec-core (RowKey::from_i64 / from_i32 / from_i16 / from_uuid / from_text) that route through rowkey::canonical, so the generated code and the proxy agree byte-for-byte.

Once this lands, rewrite examples/embedded.rs from TASK-0192.05 to use the derive, and make it the library example in the README (TASK-0192.07).
